# Nukleio Security Audit

**Repository:** EricNohara/Nukleio (`dev`)  
**Related repository:** `Nukleio-Ai-Agents` (`dev`)  
**Audit date:** September 6, 2026  
**Audit type:** Consolidated follow-up audit  
**Scope:** Open findings from the July 24 and August 22 audits, including the
app-to-agent authentication implementation and its deployment prerequisites.

## P1 — High priority

### 3. Private documents are still represented by public object URLs

Resumes, transcripts, portraits, project images, and AI outputs continue to use
public storage URLs. Make customer-document buckets private, store object paths,
and issue short-lived authorized signed URLs instead.

### 4. File validation trusts attacker-controlled metadata

Storage and image routes do not consistently verify magic bytes, decode and
re-encode images, structurally validate PDFs, reject SVG/script-capable files,
or scan content. Add exact format allowlists, byte/decode validation, strict
PDF limits, malware scanning, and `nosniff` delivery headers.

### 5. Public API limits, quotas, and bounded logging are missing

The API-key-protected public data route has no per-key, per-IP, plan, or global
limits. Add burst and monthly quotas, key scopes, bounded metadata, aggregated
or sampled usage logging, and a global abuse/cost circuit breaker.

### 6. AI payloads, responses, and upstream duration are not bounded

AI inputs and arrays remain largely unbounded, agent calls lack strict total
timeouts, and responses are read without a response-size cap. Add runtime
schemas, payload/token/output limits, `AbortController` timeouts, bounded
response reads, and reconciliation for stuck credit charges.

### 7. Headshot revision accepts an arbitrary downstream URL

Revision requests should accept a server-issued headshot ID, verify ownership,
derive the storage path server-side, and have the agent block private,
loopback, link-local, metadata, non-HTTPS, and oversized destinations.

### 8. Stripe checkout does not allowlist price IDs

The checkout route accepts syntactically valid Stripe price IDs instead of only
the configured plans. Enforce a server-side allowlist, validate the retrieved
price/product/currency/interval/amount, and protect concurrent checkout creation
with idempotency and ownership locking.

### 9. Destructive and security-sensitive actions lack recent reauthentication

Account deletion, password changes, API-key rotation, and billing-sensitive
actions should require recent authentication and MFA when enrolled. Enable
secure password-change behavior and provide out-of-band security notifications.

### 10. Unsafe authenticated default database privileges remain

Future public tables, sequences, and routines can inherit broad `authenticated`
privileges. Revoke unsafe authenticated defaults and grant only the privileges
required by each migration. Add a privilege regression check.

### 11. Direct Supabase Data API access bypasses route-level invariants

RLS limits cross-tenant access, but authenticated clients can still bypass many
route-level field, count, cache, and business-rule checks. Move invariants into
constraints or service-role RPCs, cap lengths/arrays/row counts, minimize
exposed columns, and verify course-parent ownership using both parent ID and
authenticated user ID.

### 12. API-key governance is incomplete

API-key expiration, rotation, revocation, and hashed storage exist, but scopes,
quotas, rate limits, and explicit key-level usage controls remain absent. Ensure
hashed key columns are not directly selectable through the client Data API.

### 13. Temporary and failed AI storage objects are not consistently cleaned up

Failed headshot inputs, abandoned project thumbnails, and generated objects can
remain after failed or incomplete workflows. Use temporary prefixes,
reference rows, `try/finally` cleanup, and bucket lifecycle rules.

### 14. Security regression assurance is incomplete

The repository intentionally has no automated test suite, and no CI evidence
currently proves RLS, privilege, storage-isolation, credit-concurrency,
webhook-ordering, migration, or production-build security invariants. This is a
launch assurance gap to address in a dedicated testing/CI workstream.

## P2 — Hardening and operational follow-up

### 15. Runtime input validation is inconsistent

Many routes cast parsed JSON directly to TypeScript interfaces. Adopt shared
runtime schemas, reject unknown fields, and mirror important limits in SQL.

### 16. Error responses expose internal details

Several storage, Stripe, webhook, and premium-cache routes return raw provider
or database messages. Return stable public error codes and generic messages;
send redacted details to private telemetry with request IDs.

### 17. Security headers and CSP need hardening

The CSP still permits inline scripts/styles and broad image sources. Add HSTS
after HTTPS is confirmed, `X-Content-Type-Options`, `Referrer-Policy`,
`Permissions-Policy`, and compatible cross-origin protections; replace inline
script allowances with nonces or hashes where practical.

### 18. CSRF/Origin checks are inconsistent

Cookie-authenticated mutations mostly rely on implicit SameSite behavior.
Centralize Origin or CSRF-token validation for sensitive mutations, excluding
provider-signed webhook routes.

### 19. OAuth callback construction trusts proxy forwarding headers

Use an allowlisted configured canonical origin instead of trusting arbitrary
forwarded host values, and await the OAuth signup side effect before redirecting.

### 20. Password policy is weak in committed configuration

The committed configuration permits short passwords and lacks stronger breach
and MFA guidance. Raise the minimum length, support long passphrases, reject
known-compromised passwords, and verify hosted Auth settings.

### 21. Security logging and monitoring are insufficient

Add structured, redacted audit events and alerts for authentication/recovery,
API-key changes, account deletion, storage volume, AI charge/refund anomalies,
agent failures, Stripe conflicts, and repeated authorization failures.

### 22. Dependency and build reproducibility need attention

Align Next.js and `eslint-config-next`, validate clean `npm ci` builds, run
dependency advisory and independent supply-chain scans, retain an SBOM, and
automate dependency update review. Existing Next.js dependency-chain advisories
remain a separate security workstream from the P0 agent-auth fix.

### 23. Hosted database and storage deployment drift is not continuously verified

Repository migrations are not proof that production has the same migration
versions, ACLs, RLS policies, routine overloads, function settings, bucket
visibility, or storage policies. Add deployment verification and fail releases
on security-relevant drift.

## Launch decision

**Current decision: Do not launch publicly.**

The immediate launch gates are:

1. Complete and verify the AWS IAM agent deployment.
2. Stop signup-based credit farming and add global AI abuse/cost controls.
3. Enforce storage quotas and upload limits.
4. Make private documents private and close the remaining high-priority data,
   billing, validation, and reauthentication gaps.
